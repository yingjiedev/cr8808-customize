## 1. 是否支持本机

**这是一份有旧版 CR880x 适配线索的历史网页 U-Boot 包，可以继续验证；目前不能确认它适合直接替换本机引导，也不能确认替换后能保留现有双系统启动方式。不要照附带 TXT 直接刷写。**

它与上次调研的历史文件包是同一套二进制，不是新增的另一版引导。三份文件均已逐字节比较，结果完全相同；新增证据主要是这份原始 TXT，以及对主、备引导启动标记的进一步检查。[上次调研与文件来源](cr8808-web-uboot-research.md#5-历史文件包实际下载与核验)

| 要判断的问题 | 本次结论 |
| --- | --- |
| 是不是含网页功能的 U-Boot | 主文件含网页内容、HTTP 相关代码字符串和 `192.168.10.1`，有明确静态证据 |
| 文件尺寸是否符合本机对应分区 | 符合：MIBIB 512 KiB，两个 APPSBL 均为 1280 KiB |
| MIBIB 是否匹配本机原厂备份 | 完全相同；写入相同文件不会带来新的分区布局 |

| 能否继续从当前 mtd19 启动 ImmortalWrt | 尚未确认，需要核对引导选择、FIT 配置、加载地址和内核启动 |
| 能否继续简单切槽回原厂 | 尚未确认；不能沿用原厂引导的结论 |
| 能否把包内 TXT 当作安装教程 | 不能；存在明确的分区名称错误，且需要先具备可用串口 |

### MIBIB：还是原厂双槽位表

本机原厂 `mtd1` 备份与包内 `MIBIB.bin` **逐字节相同**。文件中两份有效 Qualcomm 分区表也彼此一致，均为 22 个分区：

```text
rootfs     起始 0x00a80000   大小 0x02400000   36 MiB
rootfs_1   起始 0x02e80000   大小 0x02400000   36 MiB
overlay    起始 0x05280000   大小 0x01f00000   31 MiB
data       起始 0x07180000   大小 0x00d80000   13.5 MiB
```

因此，TXT 中称其为“合并分区”不构成实际效果的证据。若旧 U-Boot 在启动时另外改写内存中的分区信息或内核参数，仍需源码或串口日志确认。**本机没有为了匹配这份 MIBIB 而重写 mtd1 的必要。**

### 主、备引导：不是等价副本

| 项目 | `APPSBL.bin` | `APPSBL1.bin` |
| --- | --- | --- |
| 格式 | ELF32 / ARM | ELF32 / ARM |
| 入口地址 | `0x4a920000` | `0x4a920000` |
| 版本字符串 | U-Boot 2016.01，2022-12-14 | U-Boot 2016.01，2021-12-09 |
| 默认 bootcmd 字符串 | `bootipq` | `bootipq` |
| 默认 IP 字符串 | `192.168.10.1` | `192.168.31.100` |
| 网页内容 | 已发现 | 本次未核实具备与主引导等价的网页恢复入口 |
| 小米双槽位标记 | 下列五个完整字符串均未找到 | 五个均找到，另含 `bootmiwifi` 命令字符串 |

检查的标记为：`flag_boot_rootfs`、`flag_last_success`、`flag_try_sys1_failed`、`flag_try_sys2_failed`、`flag_ota_reboot`。

**这是启动逻辑差异的线索，不是仅靠字符串就完成了反汇编证明。** 目前不能据此断言主引导绝对不支持双槽位，也不能反过来假设它会读取本机现有的启动变量、自动从 mtd19 启动。

两个文件也都与本机原厂 APPSBL 备份不同。不能把 `APPSBL1.bin` 当成自己的原厂备份，更不能认为“主引导失败，备引导肯定自动救回”。是否切换引导副本取决于前级机制及配置，尚未验证。

## 3. 附带 TXT 有什么问题

初次收到的 TXT 是有效 UTF-8 文件，要求先通过 TTL 中断进入 U-Boot，再传文件刷写；因此它本身就不是一个只在 LuCI 或 SSH 里操作的教程。下面记录原文问题；后续修正版已经更正名称并补充前置条件。

最明确的错误是这行中的目标名称：

```text
包中写的是：flash 0:APPSBL1.bin
本机分区名：0:APPSBL_1
```

`APPSBL1.bin` 是电脑上的文件名，`0:APPSBL_1` 是本机分区名，两者不能混用。指出正确分区名**不等于建议现在把该文件写进去**；是否更换备引导仍需要先确定安装和恢复方案。

TXT 还称安装后 TTL 命令入口会关闭，并描述 Reset 上电、DHCP 和 `192.168.10.1` 网页入口。这些是文件作者的说明，尚未在本机实测。尤其不能以当前能通过 SSH 登录系统，代替“串口已接好、能中断并救援”的条件。

## 4. 与本机的匹配程度

有利条件：

- 本机原厂为 CR8808、`ap-mp02.1`、`xpa`，已成功运行 `redmi,ax3000` 对应的 ImmortalWrt。
- 本机为 ESMT 128 MiB SPI NAND，页 2048、块 131072、OOB 64；候选引导中存在 `F50D1G41LB(2M)` NAND 型号字符串，值得进一步核对。
- 文件尺寸、ELF 平台和入口地址具有同平台适配线索；MIBIB 与本机原厂内容完全匹配。

还没确认的关键项：

- 本机完整 NAND ID 是否匹配候选驱动，实际读写与坏块处理是否正确。
- Reset 和交换机的板级配置，是否能在 U-Boot 阶段可靠提供 LAN 网页连接。
- 主引导究竟使用哪个系统分区、是否改变分区边界，以及会否覆盖原厂槽。
- 现有 64 位 Linux 6.6.137 / ImmortalWrt 24.10-SNAPSHOT 镜像的加载和启动兼容性。不能用候选引导为 ELF32 就判定它一定不能启动 64 位内核，也不能仅因 UBI 格式相同就认定能启动。
- 安装后是否仍有串口入口、是否可恢复本机原厂引导，及恢复需要哪些前级条件。

## 5. 建议怎么继续

**如果目标是“增加网页救援，同时继续保留原厂系统和现有 ImmortalWrt”，优先采用[上一份报告的开源适配路线](cr8808-web-uboot-research.md#路线-a保留分区新增-cr8808-开源适配优先)。这份旧文件包暂列实验候选。**

若要继续验证这份包，按下面顺序推进；这些是验证要求，不是刷写命令：

1. 接好适合本机的串口，确认能读取完整上电日志、中断原厂 U-Boot，并核对 NAND ID、machid、原厂分区和环境。
2. 从源码、同板验证记录或进一步代码分析中，确认主引导对系统槽、网页写入和合并分区的实际处理。没有这些信息，不决定更换主/备引导的组合。
3. 确认候选镜像适用的加载和恢复方法，再验证 Reset、LAN、HTTP 以及当前 factory UBI 的启动；不能直接把 ELF 入口地址拼成 `go` 命令试跑。
4. 只有明确了写入边界、系统迁移和原厂恢复方式，才制定持久化安装步骤。若最终采用合并分区路线，应按可能需要重装系统、原有切槽恢复不再适用来设计。

**当前判断：它不是错平台文件的明显反例，有继续验证的价值；但不满足本机“直接照教程刷、现有双系统保持可用”的完成条件。** 本次没有新增编译、运行或刷写验证，设备状态保持原厂 U-Boot＋mtd19 的 ImmortalWrt。
